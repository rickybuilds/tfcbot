# Optional private HLTV registry handoff

Current notifications include persisted HLTV scanner outcomes: completed-with-no-candidates, completed-with-candidates, and failed analysis. Candidate details are sourced only from `statistics.scanner.findings`; concussion markers, gap findings and firing statistics are not scanner candidates. The private alert title is `NN//TFC · HLTV ANALYSIS COMPLETE` or `NN//TFC · HLTV ANALYSIS FAILED`, and every candidate message includes the configured HTTPS Investigation Console link plus the human-review disclaimer. Existing `hit_evidence_review` notifications remain supported: they report strict hit-evidence rates, distinct concussion-window coverage and personal baselines counted in **games**. The sender suppresses unsent legacy `aim_gap_review` alerts with an auditable reason and preserves already posted messages/manual alerts. See the website repository's `docs/HLTV-HIT-EVIDENCE-ALERTS.md` for the hit-evidence policy.

The optional website `HLTV_AIM_GAP_REVIEW_ENABLED` rule now queues `aim_gap_review` alerts for verified conc/non-conc aim-near gaps below 10 percentage points. Update this bot before enabling that website flag. Its private alert includes player, weapon/class, counts, rates and review link. Small samples still flag; the below-25 note appears only if either side has fewer than 25 eligible firing events. These are configured human-review triggers, not cheating verdicts. Existing alert enablement, channel privacy checks, allowlists and disabled mentions remain required. The website's `api/scripts/flagHltvAimGaps.js --apply` backfills stored comparisons without re-decoding; repeated findings are deduplicated.

The existing `services/hltvFetch.js` SFTP retrieval remains the only downloader. Automatic and manual match recaps pass their canonical match ID. When `HLTV_REGISTRY_ENABLED=true`, downloads finalize into `HLTV_STORAGE_ROOT/incoming/<uuid>/`; after ZIP creation closes, `ready.json` publishes metadata to the website's separate worker. ZIP attachment delivery remains unchanged; retained raw demos are never recursively removed by `cleanupResult`. No analysis runs inside Discord delivery. Without flags/match metadata the existing temporary workflow remains.

Configure `.env.example` settings in the bot's existing `.env`. The website API and worker need the same private filesystem mount and SQLite registry database. Initialize the website registry first. Do not use NFS for SQLite WAL. Run bot/API/worker as the same dedicated OS user or provision inheritable ACLs (generated directories are 0700, manifests 0600). Use service-owned permissions and keep storage outside repositories/static roots. Bot validates its own code root and configured `HLTV_PUBLIC_ROOT`. Storage/headroom failure logs an error and continues the existing Discord delivery without retention; monitor those errors.

**New dedicated channel environment setting: `HLTV_REVIEW_ALERT_CHANNEL_ID`.** Create a new private Discord text channel and paste its actual ID. No channel is created automatically and no generic ADMIN channel is used. Set the explicit comma-separated `HLTV_REVIEW_ALLOWED_USER_IDS`. Deny everyone View Channel; remove all role View Channel allows; grant only approved user members and bot member access. Bot needs Send Messages. Guild owners/administrators inherently bypass Discord restrictions, so review those privileges too. Update channel permissions when removing reviewers; an environment allowlist alone cannot revoke Discord's access to channel history.

Keep `HLTV_ALERTS_ENABLED=false` during validation. When enabled, bot polls only the durable registry outbox every 30 seconds and refuses unsafe channel overwrites. It sends scanner, manual review/report, hit-evidence and capacity alerts only to the configured private review channel, with no automatic mentions. Claims expire after two minutes; failed sends retry with backoff, stop after 12 failures, and preserve their alert ID. At-least-once delivery can repeat an alert after a send/ack crash, but repeated worker cycles and reanalysis results are deduplicated by analysis run identity; a new reanalysis run gets one new notification. No historical runs are backfilled automatically and no tests send production messages.

The website creates scanner outbox rows only after a terminal persisted analysis result. A valid scanner payload with zero findings produces a clean completion summary; a valid payload with findings produces bounded player/time/duration details; a failed run produces a failure category and safe next action; statistics-only legacy payloads produce no scanner-complete notification. The website and bot must use the same private SQLite registry database. Optionally set `HLTV_ANALYSIS_CHANNEL_ID` for no-candidate completion summaries; candidate and failure details always use `HLTV_REVIEW_ALERT_CHANNEL_ID`, which must remain private. Otherwise all scanner notifications use the private review channel. Required settings remain `HLTV_REGISTRY_ENABLED`, `HLTV_ALERTS_ENABLED`, `HLTV_REGISTRY_DB`, `HLTV_REVIEW_ALERT_CHANNEL_ID`, `HLTV_REVIEW_ALLOWED_USER_IDS`, and HTTPS `HLTV_REVIEW_BASE_URL`. Deploying the schema is additive; do not run a historical backfill.

Website operations, cleanup safeguards, authorization, deployment, backup and parser contract are documented in `nonamepickup-web/docs/HLTV-REVIEW.md` and `HLTV-ANALYZER-CONTRACT.md`. All cleanup is owned by that subsystem and disabled by default. Do not add another raw-demo cleanup cron. The external GoldSrc parser/viewer is not bundled; there are no detectors or fabricated findings. Manual review works while analysis is unsupported.

On an interrupted ZIP, `pending.json` and originals remain private; stop the bot, inspect and backfill the local manifest with the website CLI. `.part` files or failed-upload ZIPs need operator review. The bot's three-second close buffer and downloaded-size validation do not prove the remote recording stopped. See [HLTV recording finalization](HLTV-FINALIZATION.md) for the opt-in finalization guard and read-only original-source checks.

Test: `node --test test/hltvReview.test.js`. Full bot tests remain `npm test`.

The bot now logs effective collection status at startup and confirms private original-file handoff/publication on each match recap. Verify the actual PM2 script/cwd (`pm2 describe tfcbot`) before pulling or editing `.env`; a different checkout or cwd can leave the old temporary workflow active. The web worker has an opt-in `HLTV_MANUAL_RETENTION_ENABLED` policy for automatic normal seven-day expiry while no analyzer exists, plus a five-minute cron installer. Configure that policy in the website `api/.env`, not the bot. Holds, evidence and flagged demos remain protected. This does not alter the 30-day pickup CSV archive policy or delete the existing parser raw logs. See the website runbook for rollout; no automatic cleanup flag is enabled by this commit.
